# Cost & Abuse Audit — HarmonyAI

> **Update:** the app has since been migrated off Gemini onto Groq (see `backend/src/services/llmClient.ts`). Every "Gemini call" in the findings below is now a Groq call instead — the routes, auth gaps, and missing rate limits are **unchanged and still exploitable**; only the provider name changed. Groq's free tier still has real per-minute/per-day token limits, so an unauthenticated flood still breaks the feature for real users (denial of service) even though it may no longer produce a dollar bill the same way a paid Gemini tier would. Treat every CRITICAL/HIGH finding below as still open.

Scope: every route file under `backend/src/routes/`, `backend/src/index.ts` (global middleware), every controller that calls into `GeminiEmbeddingProvider`/`GEMINI_API_KEY`-backed services, and `authController`/`authService`.
Method: traced each route's middleware chain (`protect` / `optionalAuth` / none) and cross-referenced it against what the underlying controller/service actually does — an LLM call, a DB write, an unbounded query, etc. — rather than assuming "has a rate limiter" means "is protected."

## What already exists (so the fixes below build on it, not duplicate it)

- `backend/src/index.ts` applies `helmet()`, a **global** `express-rate-limit` of 500 requests / 15 min (keyed by IP, the library default), and a **stricter** 30 requests / 15 min limiter scoped to `/api/auth/*`.
- `express.json({ limit: '1mb' })` caps request body size app-wide.
- Prompt/message length is already capped server-side in the two places that matter: `MAX_MESSAGE_LENGTH = 500` in `assistantController.ts`, and a 500-char cap on the AI playlist `prompt` in `playlistController.ts`. So per-call payload size is not the exposure — **call frequency and missing auth are**.
- `songController`'s pagination `limit` looks uncapped in the controller (`const limit = q.limit || 20;`) but `SongService.getAllSongs` clamps it to `Math.min(100, limit)` before it ever reaches Mongo — verified this is actually enforced at the query layer, not just cosmetic. No fix needed there.
- Login/password error messages are already generic ("Invalid email or password") for both "no such user" and "wrong password" — no enumeration via login. There is no password-reset flow in the codebase at all (no route, no email service), so that sub-category doesn't apply here.
- There is no email or SMS sending anywhere in the backend (`grep` for nodemailer/sendgrid/twilio/mailer across `backend/src` returns nothing) — that entire abuse category is not applicable to the current app.

## Findings

| Endpoint | What one call costs you | Abuse scenario | Projected damage from one night | Severity | Exact limiter to add |
|---|---|---|---|---|---|
| `GET /api/search/semantic` (`searchRoutes.ts` → `searchController.semanticSearch` → `SemanticSearchService` → `EmbeddingService.generateEmbedding` → Gemini) | One Gemini embedding API call per request whenever `GEMINI_API_KEY` is configured (the whole point of the feature — without it, this silently degrades to a free local hash, so the cost only exists once you actually enable semantic search in production). | This route has **zero middleware** — not `protect`, not even `optionalAuth`. It's a bare `GET` with a query string; no token, cookie, or body required. A one-line loop (`while true; curl .../api/search/semantic?q=x; done`, or a handful of parallel workers across a small botnet/proxy pool) hits it as fast as the network allows. The only thing standing between this and unlimited spend is the *global* 500-req/15-min-per-IP limiter, which a handful of rotating IPs trivially clears. | At 500 req/15min from a single IP = 48,000 requests/day from that one IP alone; with 10 rotating IPs (free proxies, mobile hotspot cycling, or just 10 friends' laptops), ~480,000 Gemini embedding calls overnight. Even at fractions of a cent each, that's a real bill, and it also exhausts your Gemini quota, breaking the feature for real users. | **CRITICAL** | Add `protect` (require login) — this alone cuts the attack surface from "anyone on the internet" to "someone with an account." Then add a dedicated `rateLimit` for this route only, keyed by user ID rather than IP: e.g. 20 requests / 5 min per user via a `keyGenerator: (req) => req.user._id`. Also cache identical queries for a short TTL (e.g. 60s) since repeated identical searches are common and shouldn't re-hit Gemini. |
| `GET /api/search/discover`, `GET /api/search/unified` (`searchRoutes.ts` → `unifiedDiscovery`, mode `semantic`/`all`/`hybrid`) | Same Gemini embedding cost as above whenever the mode involves semantic search (the default mode is `'all'`, which includes semantic). | Uses `optionalAuth`, so it's callable **without** a token — same scriptable loop as above, just with a `mode` query param. | Same order of magnitude as the finding above — this is effectively a second door into the identical cost center. | **CRITICAL** | Same fix: require `protect` (or at minimum, if anonymous discovery is a deliberate product decision, force `mode=keyword` for unauthenticated requests server-side and only allow `semantic`/`hybrid`/`all` modes once `req.user` exists), plus a per-user/per-IP limiter dedicated to this route (e.g. 30 req / 5 min). |
| `POST /api/assistant/chat` (`assistantRoutes.ts` → `handleAssistantChat` → `AssistantIntentService`/`MultiStepAssistantService` → Gemini) | One or more Gemini chat completion calls per request (multi-step requests can trigger several tool-calling round-trips per single HTTP call, so the true cost-per-request can be a small multiple of a single call). | `optionalAuth` — fully callable anonymously. A script POSTs `{ "prompt": "..." }` in a tight loop; there's no session, cookie, or account needed. Only the global 500/15min/IP limiter applies. | Same rotating-IP math as the search findings, but worse per-request cost since this is a full chat completion (and sometimes multiple), not a single embedding vector: at 500 req/15min/IP × 10 IPs overnight, this is the most expensive single line item in a realistic attack, easily the largest of the night's damage. | **CRITICAL** | Require `protect`. Add a dedicated per-user limiter (e.g. 15 messages / 5 min, generous enough for real conversational use, far too slow to be worth scripting). Also consider a **daily** cap per user (e.g. 200 messages/day) enforced server-side and checked before the Gemini call, not just a sliding window, since a sliding window alone still allows sustained 24/7 hammering at just-under-the-limit. |
| `POST /api/recommendations/assistant` (`recommendationRoutes.ts` → `processContextualAssistantRequest` → `ContextualAssistantService` → Gemini) | One Gemini call per request. | `optionalAuth` — anonymous, same as above. This is a second, easy-to-miss door to the same underlying Gemini spend, separate from `/api/assistant/chat` but with identical exposure. | Comparable to the `/api/assistant/chat` finding — treat as additive damage on top of it, since an attacker who finds one will likely find and use both. | **CRITICAL** | Same fix as `/api/assistant/chat`: require `protect`, add a per-user limiter, and — since these two routes both ultimately spend the same Gemini budget — consider a single shared per-user "AI calls" counter/limiter used by both, so a user can't just switch endpoints to double their effective quota. |
| `POST /api/playlists/ai-generate`, `POST /api/playlists/generate` (`playlistRoutes.ts` → `generateAIPlaylistEndpoint` → Gemini via `aiPlaylistGenerationService`) | One Gemini call per request to interpret the prompt into structured playlist parameters, plus the DB work to actually assemble the playlist. | Already requires `protect`, so this needs a real (or compromised) account — meaningfully better than the routes above. But there is no route-specific limiter: an authenticated user (one account is enough) can call this up to the global 500/15min/IP ceiling. | One compromised or maliciously-created free account can drive ~48,000 Gemini calls/day before even needing multiple accounts or IPs. | **HIGH** (lower than the anonymous routes only because auth is already required, not because the cost-per-call is smaller) | Add a per-user limiter scoped to this route: e.g. 10 generations / hour, 30/day. This is a generous ceiling for genuine use (nobody generates dozens of playlists an hour) and makes scripted abuse pointless. |
| `GET /api/admin/recommendations/evaluate` (`adminRecommendationRoutes.ts` → `evaluateRecommendationStrategy`) | Not an LLM call, but a genuinely expensive one: it runs content-based, collaborative, and/or hybrid recommendation scoring across the catalog for a `k` result count that has **no upper bound** (`const k = isNaN(q.k) || q.k < 1 ? 10 : q.k;` — no `Math.min` cap, unlike the search routes). | The route comment says "Protected Development/Admin," and it does require `protect` — but there is **no admin/role field anywhere in the `User` model** (`grep -n "role\|isAdmin" backend/src/models/User.ts` returns nothing) and no role check in the route. Any authenticated user — including one who just self-registered seconds ago — can call this "admin" endpoint, and can pass an arbitrarily large `k` (e.g. `?k=999999`) to force a maximal, repeated computation over the full song/user/history collections. | Not a metered third-party cost, but sustained DB/CPU load from repeated large-`k` calls can degrade the app for everyone or spike your database hosting bill (connection/CPU-time based tiers), especially if run in a tight loop overnight. | **HIGH** | Two independent fixes, both needed: (1) add an actual `role` field to `User` (e.g. `role: 'user' \| 'admin'`, default `'user'`), and an `requireAdmin` middleware that checks it, applied to this route instead of bare `protect`. (2) Cap `k` with `Math.min(50, k)` the same way the search controllers already do, and add a route-specific rate limit (e.g. 20 req/hour) regardless of role, since even legitimate admin dashboards shouldn't need tighter-than-that polling. |
| `POST /api/auth/register` (`authRoutes.ts` → `authController.register` → `AuthService.register`) | Cheap per call (a bcrypt hash + one DB write), but it's the account-creation door that every other per-user limiter above depends on to actually mean something. | Distinguishable responses: an existing email returns `400 "User with this email already exists"`, a new one returns `201` and a session token. This lets a script enumerate which emails have HarmonyAI accounts by POSTing a list of guesses and reading the status code — and, separately, since there's no CAPTCHA/bot check and no per-IP signup cap beyond the shared 30-req/15min `authLimiter`, a script can mass-create throwaway accounts (28 accounts/15min/IP is still ~2,700/day from one IP) specifically to get past the per-user limiters recommended above for the AI routes — i.e. weak signup protection undermines every other fix in this table if left as-is. | Low direct dollar cost from registration itself, but it's the multiplier that makes every "require `protect`" fix above only as strong as signup is hard to automate. | **MEDIUM** (email enumeration) / **HIGH** (as an amplifier for the AI-route fixes, since free accounts are the workaround) | Keep the account-creation response generic in *timing and shape* if you want to fully close enumeration (e.g. always return 201-shaped responses and email a "you already have an account" notice instead — bigger change, optional). At minimum: add a dedicated, tighter limiter on `/api/auth/register` specifically (the shared 30/15min `authLimiter` also covers `/login`, so a login-heavy legitimate user session eats into the budget an attacker needs for mass signup, and vice versa) — split them into two limiters, e.g. register: 5/hour/IP, login: 10/15min/IP. Add a CAPTCHA (hCaptcha/Turnstile, both free) on `/register` before it's ever exposed publicly with real Gemini costs behind it. |
| `POST /api/auth/login` (`authRoutes.ts`) | Cheap per call (bcrypt compare), but bcrypt is deliberately slow — at scale, a credential-stuffing run against many usernames is a CPU cost, not just a security risk. | Shares the same 30-req/15min `/api/auth` limiter with `/register` (see above) — keyed by IP only, so a distributed attempt (many IPs, few attempts each) isn't slowed at all, and there's no per-account lockout (an attacker distributing attempts across IPs but targeting one email is not throttled per-account). | Bounded by IP-level throttling for single-source attacks; distributed credential stuffing is not meaningfully slowed today. | **MEDIUM** | Add a per-account (per-email) failed-attempt counter independent of IP — e.g. 10 failed attempts on one email within 15 minutes triggers a short lockout or a mandatory delay, regardless of how many different IPs those attempts came from. This is on top of, not instead of, the existing IP-based limiter. |

## What one full night of unmitigated abuse could look like

Combining the CRITICAL findings (they're independent doors to the same Gemini budget, so an attacker would likely use several at once, not just the worst one): a modest operation running from 10 rotating IPs, each staying just under the 500-req/15-min global ceiling, sustained for 8 hours, is on the order of **300,000+ billable Gemini calls in one night**, split across chat completions, contextual-assistant calls, and embedding lookups — before touching the authenticated-only playlist-generation route at all. The actual dollar figure depends on your Gemini pricing tier, but the point of every fix above is the same: **none of the four CRITICAL routes should be reachable without `protect`, and none of them should trust the shared global limiter to be "the" rate limit** — each needs its own per-user ceiling sized for real usage, not for defense.

## Suggested limiter shape (for when you implement)

All of the "add a per-user limiter" fixes above can share one small utility rather than five bespoke configs:

```ts
// backend/src/middlewares/aiRateLimiter.ts (illustrative — not yet implemented)
import rateLimit from 'express-rate-limit';

export const perUserAiLimiter = (max: number, windowMs: number) =>
  rateLimit({
    windowMs,
    max,
    standardHeaders: true,
    legacyHeaders: false,
    keyGenerator: (req) => req.user?._id?.toString() ?? req.ip, // falls back to IP only if somehow unauthenticated
    message: { success: false, message: 'You are sending requests too quickly. Please slow down.' },
  });
```

Applied per-route with numbers sized to the table above (e.g. `perUserAiLimiter(15, 5 * 60 * 1000)` on `/api/assistant/chat`). This is a proposal for the fix pass, not yet implemented — flagging here so the shape is agreed before writing it.
