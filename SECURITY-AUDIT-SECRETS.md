# Secrets Audit — HarmonyAI

> **Update:** the app has since been migrated off Gemini onto Groq (see `backend/src/services/llmClient.ts`). `GEMINI_API_KEY` is no longer read anywhere in the codebase — the rotation note for it below is now moot (nothing depends on it any more). `GROQ_API_KEY` is the new key to protect; nothing in this audit found it hardcoded or committed anywhere, since it didn't exist yet at audit time.


Scope: `frontend/`, `backend/`, full git history (`git log --all`), build output.
Method: pattern search for key/token/password/connection-string formats across source, `.env*` files, and every commit that ever touched an `.env*` path; manual review of every `process.env.*` read site; check of what `VITE_*` variables ship into the browser bundle.

## What was checked and came back clean

- **No API keys, tokens, or connection strings with real credentials found in any tracked source file** (`.ts`, `.tsx`, `.js`, `.json`) — searched for Stripe/OpenAI/Anthropic/Google/AWS/GitHub/Slack key prefixes, `mongodb://`/`mongodb+srv://` with embedded credentials, and `postgres://user:pass@` patterns. None present.
- **`GEMINI_API_KEY`** (`backend/src/services/aiPlaylistGenerationService.ts`, `embeddingService.ts`, `assistantIntentService.ts`, `contextualAssistantService.ts`, `llmAssistantConnectorService.ts`) is read exclusively via `process.env.GEMINI_API_KEY`, always defaults to `''` (never a hardcoded fallback key), and every consumer checks `hasGeminiKey` before calling out. This is not a code-level leak, but see the abuse-audit doc — it's an endpoint-cost problem, not a secrets problem.
- **`.gitignore`** correctly lists `.env` at the root, which covers `backend/.env` and `frontend/.env` recursively. Both are confirmed untracked (`git ls-files` shows neither).
- **Frontend bundle**: only `VITE_API_BASE_URL` (a plain URL, not a secret) is exposed via `import.meta.env` — grepped every `VITE_` reference in `frontend/src`. No privileged key is prefixed with `VITE_`, so nothing sensitive is being bundled into the browser JS.
- **No Supabase credentials found yet** — `@supabase/supabase-js` is already a dependency in `backend/package.json`, presumably staged for the upcoming migration, but no Supabase URL/anon key/service-role key exists anywhere in the repo yet. **Flag for the migration itself**: when Supabase credentials are added, the service-role key (which bypasses Row Level Security) must never go in anything prefixed `VITE_`/`NEXT_PUBLIC_` or otherwise reach the frontend bundle — only the anon key belongs client-side, and only if RLS policies are actually written and enabled before that key does any privileged work.

## Keys to rotate — non-negotiable

Anything that ever appeared in a commit is burned, even if a later commit removed it. For this repo, that's a short list:

1. **`JWT_SECRET`** — the value `***REMOVED-LEAKED-JWT-SECRET***` is permanently recoverable from git history (commit `6e1e14b`) and is also the value currently live in `backend/.env`. Generate a new one (`openssl rand -base64 48`), put it only in the gitignored `.env`, and understand that **every JWT ever issued under the old secret becomes valid-looking garbage** the moment you rotate — that's the point, since anyone holding the old secret could otherwise mint tokens for any `userId` forever. There's no user-facing "session revocation" needed beyond this, since HarmonyAI has no refresh-token/session store to also invalidate (JWT is the only ledger).
2. **`GEMINI_API_KEY`** — no evidence it ever touched a commit or the frontend bundle, so this is a precaution rather than a confirmed leak: rotate it anyway if it has ever been pasted into a shared chat, ticket, screenshot, or a `.env` that was zipped/emailed outside this repo. If you're confident it never left `backend/.env` on this machine, it doesn't need rotating on the audit's evidence alone.
3. Nothing else qualifies — no database credentials, third-party API keys, or webhook secrets were found anywhere in tracked files or history.

## Note for the upcoming Supabase migration

Since you're about to move off MongoDB: bake the following into the migration from day one rather than retrofitting it —
- Service-role key stays server-side only, read from `process.env`, never given a `VITE_`-prefixed twin.
- Anon key is the only Supabase credential allowed in `frontend/`, and only after RLS policies are written for every table it can touch — an anon key with no RLS is equivalent to an open database.
- Add `.env` scanning (gitleaks or truffleHog) as a pre-commit hook *before* the migration branch starts collecting new connection strings, so the same "real value pasted into an example file" mistake that produced finding #1 can't repeat with Supabase credentials.
